# 설계서 대비 구현 현황

첨부 문서는 제품 요구사항과 검토 중인 설계의 입력으로 사용했습니다. 문서 안의 명령·외부 시스템 접근 예시는 자동 실행 지시로 취급하지 않았습니다. 회사 환경 배포나 외부 계정 변경을 수행하지 않았습니다.

이 저장소는 설계의 핵심 관리·배포 흐름을 실제 로컬 서버로 구현한 **개발 단계 결과물**입니다. 현재 빌드 성공이나 로컬 테스트 통과는 전사 운영 승인 또는 회사 연동 성공을 의미하지 않습니다.

## 적용한 설계

| 설계 항목               | 현재 구현                                                                                                                                    |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 프로젝트 CRUD·역할·멤버 | 서버 권한 검사, OWNER 1인, MANAGER 지정은 OWNER만 가능, EDITOR 게시·설정 금지                                                                |
| 관리자 소유자 이전      | 트랜잭션 처리, 이전 소유자 권한 제거 또는 명시적 역할 유지, 토큰 폐기, 앱 공개 범위·개인 데이터 owner 유지                                   |
| 앱·데이터 동시성        | 앱 `version`과 문서 `etag`, If-Match 검사, 활성 리비전의 조건부 갱신                                                                         |
| 배포 패키지             | ZIP으로 source/, dist/, manifest.json, sbom.cdx.json 보관. SHA-256 파일별 재검증                                                             |
| 불변 리비전             | UUID 경로에 검증 결과를 원자적으로 이동. 파일 0440, 새 경로 사용, 기존 리비전 덮어쓰기 API 없음                                              |
| 업로드 제한             | 50 MiB 압축, 200 MiB 총 해제, 100 MiB dist, 파일 5,000개, 단일 파일 20 MiB, 깊이 20                                                          |
| 정적 코드 검사          | ZIP traversal·링크·특수 파일·중복 경로·해시·외부 자산·eval·iframe·Service Worker·비밀키 패턴 검사. 정적 검사는 완전한 의미 분석이 아님       |
| 게시·롤백               | READY 이후 명시적 게시. R2 승인자 1인, R3 데이터 승인자+플랫폼 관리자 2인. 자기 승인 금지. 승인 시 앱 버전과 운영 리비전 재검사              |
| 데이터                  | PERSONAL / APP_SHARED / OWNER_WRITE_SHARED_READ. 관리 화면과 런타임의 조회 정책 분리. 64 KiB/문서, 앱 10,000개·512 MiB, soft delete·7일 복구 |
| 런타임                  | 별도 Express 리스너, 앱 경로 접근 검사, 별도 쿠키, 제한된 CSP, DB 프록시·CSRF, 브라우저 신원 헤더 무시                                       |
| 미리보기                | 작업 멤버만 접근. `connect-src 'none'`으로 모든 API 통신 차단. 현재 구현에서는 읽기 API도 허용하지 않음                                      |
| 차단                    | 앱 실행·DB 쓰기·Ollama 활성화를 매 호출마다 검사. STaRT·Trace는 미연결                                                                       |
| 감사                    | SQLite INSERT와 해시 체인. UPDATE/DELETE 거절 트리거. 본문 대신 필드·해시 기록                                                               |
| 폰트                    | 로컬에 묶은 Pretendard, Manrope. 외부 CDN 의존 없음                                                                                          |

## 확정되지 않은 환경과 남은 구현

### 인증

- 현재는 `APP_MODE=local`의 개발용 계정 선택과 8시간 세션만 구현합니다.
- `APP_MODE=production`은 시작을 거절합니다. 개발 계정 선택을 실제 인증으로 사용하면 안 됩니다.
- Keycloak Authorization Code + PKCE, 관리·실행 클라이언트 분리, 암호화된 서버 토큰 저장, refresh·로그아웃·퇴직자 동기화, 토큰 교환 audience/scope 검증은 구현 전입니다.
- MCP는 loopback HTTP만 허용하며 기본 체험 사용자 김하늘로 동작합니다. PKCE 브라우저 로그인과 OS 키체인 저장은 구현 전입니다.
- 로컬 관리 화면은 `localhost`, 실행 앱은 `127.0.0.1`로 열어야 쿠키 호스트가 분리됩니다. 운영에서는 실제로 서로 다른 HTTPS 호스트를 사용해야 합니다.

### 회사 DB·프록시

- 로컬 영속 DB는 Node `node:sqlite`를 사용합니다. 회사 DBMS가 미확정이므로 PostgreSQL/MariaDB 어댑터는 아직 없습니다.
- PostgreSQL RLS, 분리된 DB 계정, 전용 데이터 Repository, 회사 마이그레이션 배포 절차가 필요합니다.
- STaRT Capability는 승인 목록 외에는 거부합니다. 실제 helper 정의·요청 및 응답 schema·토큰 교환·톨게이트 호출은 연결 전입니다.
- 사용자의 후속 요청에 따라 AI는 `OLLAMA` 공급자를 우선 구현했습니다. 모델 선택, 실제 응답 생성, 런타임 프록시와 SDK, 토큰 예산·한도·감사를 지원합니다. 상세 계약은 [Ollama 안내](OLLAMA.md)에 있습니다.
- 기존 Trace 서비스/개인 토큰 A/B와 직접 호출 C는 아직 실행하지 않습니다. 과거 서비스 토큰 암호화 API는 유지하되 Ollama에서 사용하지 않으며 UI의 추후 연동 항목으로 접었습니다.
- Ollama는 SQLite에서 프로젝트별 일일 예약·정산, 프로젝트/전체 동시성, 사용자별 분당 한도를 적용합니다. Trace 서비스 토큰 과금, 스트리밍, 개인 토큰 수명주기, 사용자별 일일 예산 및 Mode C 정책은 별도 구현이 필요합니다.
- DB 런타임 rate limit은 단일 프로세스 메모리 기반입니다. Ollama는 DB 기반 제한을 사용합니다. 재시작·다중 프로세스에 걸친 정확한 제한에는 DB/공유 저장소가 필요합니다.

### 배포·실행

- 설계서의 `tar.zst` 중첩 패키지 대신 Node 환경에서 검증 가능한 ZIP 형식을 사용합니다. 공개 API의 업로드 세션 3단계는 로컬 단일 multipart `/deploy`로 통합했습니다.
- 플랫폼 서버 프로세스는 Node/Express입니다. 설계의 Spring Boot는 가능한 구현안으로 제시된 것으로 해석했으며, 회사 표준이 Java라면 백엔드를 포팅해야 합니다.
- SBOM 구조·해시는 검증하지만 회사 승인 의존성, CVE, 라이선스 정책, 백신 검사는 연결하지 않았습니다. 검증 경고에 이를 명시합니다.
- 승인된 빌드 스크립트와 base path를 로컬 도구에 전달합니다. 산출물과 소스의 재현 가능한 빌드 증명은 제공하지 않습니다.
- 실행 서버는 DB의 활성 포인터에서 파일을 제공합니다. nginx auth_request, 원자적 symlink, 자산 인증 캐시, 이전 해시 자산 보존/GC, 업로드 재시작 복구·orphan 정리는 운영 어댑터 구현 전입니다.
- 전체 접근 로그·거절 감사·실행 지연 시간·p95·디스크·감사 스풀 지표는 아직 완성되지 않았습니다. 화면에서는 실제 데이터 사용량·DB 호출·Ollama 토큰과 요청 수를 표시합니다.

### 데이터·감사·운영

- 문서 목록은 안정적인 문서 ID cursor를 사용합니다. 설계의 created_at/updated_at 정렬 및 모든 top-level 조건을 포함한 관리 UI 쿼리 빌더는 미구현입니다. 런타임에서는 최대 3개의 equality 조건을 지원합니다.
- 컬렉션 모드는 생성 시 확인하며 **생성 후 항상 불변**입니다. 설계서의 ‘데이터가 없을 때 모드 변경 가능’보다 보수적입니다.
- 관리자 그룹 권한 대신 개인 사용자 단위 권한만 구현합니다. 그룹 검색·동기화는 Keycloak 연결과 함께 추가해야 합니다.
- 감사 writer 별도 계정·프로세스·내구 스풀·중앙 앵커는 구현 전입니다. 로컬 DB 트리거는 DB 파일을 제어하는 운영자에 대한 위변조 방지를 보장하지 않습니다.
- 백업·복구, 모니터링·경보, 감사 저장소 장애 fail closed, TLS·systemd·nginx 실환경 검증, 전사 2배 부하 시험은 미완료입니다.
- 소유권 이전 때 현재 구현은 토큰 명의 구분 없이 기존 LLM 토큰을 폐기합니다. 앱 자체 명의 토큰을 유지하는 예외 정책은 연결 전입니다.

## 회사 연동을 시작할 때 필요한 입력

1. 회사 DB 종류·버전, 별도 스키마와 계정 정책.
2. Keycloak issuer, realm, 버전, 관리·실행·MCP 클라이언트 ID, 인사팀/재직/승인자 클레임 형태.
3. 관리·실행 HTTPS 호스트 및 nginx 구성.
4. 초기 STaRT helper 3–5개, 데이터 등급과 저장/LLM 전달 정책.
5. 트레이스게이트 API 계약과 토큰·스트리밍·예산 정책.
6. 독립 감사 계정·중앙 로그 목적지, 보존·백업·복구 정책.

이 항목을 연결하고 설계서 §17의 보안·연동·복구 게이트를 통과하기 전에는 전사 공개를 허용하는 production 모드를 추가하면 안 됩니다.
